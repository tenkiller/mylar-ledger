# Mylar Ledger

Personal comic collection catalog and price tracker. Local-first Preact PWA (Dexie) syncing to a
Hono + `node:sqlite` server; deployed target is Fly.io (single machine + volume).

## Commands

- `npm run lint | typecheck | test | build` (root, all workspaces). All must pass clean.
- Dev: `npm run dev -w @mylar/api` (127.0.0.1:8787), `npm run dev -w @mylar/web` (proxies /sync).

## Style

- ESNext syntax. No semicolons (Prettier enforces: `npm run format`).

## Task hand-offs (Linear)

- When I assign a code task to the user (a piece reserved for them under the global Hands-On
  Learning rule, or anything I say is "yours"), create a Linear issue for it in the same turn:
  team `BRE`, project `Mylar`, assignee `me`. Put the issue identifier in my reply.
- Search `list_issues` (project `Mylar`) first; update a matching issue instead of creating a
  duplicate.
- Title is imperative and specific. The description is for a human reader, in short sentences:
  goal, why it is theirs, the files involved, the approach and pitfalls (the hints I gave), and a
  "Done when" checklist. Branch name and file list go in a collapsible "Agent notes" section.
- Only for code tasks handed to the user. No issues for my own work, questions or explanations.
- Check `list_issue_statuses` before setting a status. Mark an issue done only after the user
  confirms the work is complete.

## Invariants

- Server is authoritative; each client holds a full local copy. Writes go through `saveMutation`
  (validates, writes locally + queues outbox in one transaction). Never write synced tables directly.
- Outbox rows are deleted only after the server acks. A failed sync must never drop queued writes.
- Conflicts: last-write-wins per row on `updatedAt`. Timestamps are fixed-width UTC strings
  (`YYYY-MM-DDTHH:mm:ss.sssZ`) so string comparison is chronological; do not loosen the format.
  Known, accepted: an exact `updatedAt` tie with different content on two devices leaves them
  diverged (the server keeps the first push, a client keeps its local row). Not worth fixing for
  one user; revisit if a second writer is ever added.
- LWW replaces the whole row, by design: concurrent edits to different fields on two devices lose
  one side, and a later edit from a stale device (no `deletedAt`) resurrects a deleted row. A test
  pins the resurrection. Per-field merge would be a protocol change; not worth it for one user.
- Deletes are tombstones (`deletedAt`), never row removal. Price snapshots are append-only.
- One global `seq` orders changes across all tables. Cross-table references are deliberately not
  foreign keys (offline clients can push children before parents).
- `COLUMNS` in `packages/api/src/sync.ts` must match the real SQLite schema (a test enforces it).

## Schema changes

- Before first deploy, migration 0 may be edited in place. After first deploy: append-only
  migrations, never edit an applied one.

## Auth

- Single user. Password verified with scrypt (hash in `AUTH_PASSWORD_HASH`, generated by
  `npm run hash-password -w @mylar/api`); server-side sessions in SQLite (only a SHA-256 of the
  token is stored) via an `__Host-session` cookie: HttpOnly, Secure, SameSite=Strict.
- 90-day sliding lifetime with a 1-year absolute cap; the cookie is re-issued when the expiry
  slides. Rotating the password invalidates every session (fingerprint stored per session).
- Login is rate limited (5 failures / 15 min per IP, 30 / hour globally; IPv6 counted per /64),
  checked before any scrypt work, with at most 2 concurrent verifications (memory).
- `/sync/*` requires a session. `/healthz` and the static shell are public. The `auth` option of
  `createApp` is required with no default; do not make it optional.
- Fail closed: the server refuses to start without a valid hash. `AUTH_DISABLED=true` is honored
  only when `HOST` is loopback and is for local development only.
- Offline: a 401 never drops queued writes (`SyncAuthError`); the app opens offline without
  signing in, so local data is protected by the device lock, not by this login.
- Passkeys are deferred; keep session creation independent of the password check.

## Hard stops

- The server defaults to loopback and the image sets no `HOST`; only compose sets it (with a
  loopback-only published port). Do not weaken that or the auth fail-closed checks.
- Requests are rejected unless the Host is in `ALLOWED_HOSTS` (default: loopback names), unsafe
  methods must be same-origin (`Sec-Fetch-Site`/`Origin`), and `/sync/push` and `/auth/login`
  require `application/json`. Keep these when changing auth (CSRF, DNS rebinding).
- Set `TRUST_PROXY_HEADER` (e.g. `Fly-Client-IP`) only behind a proxy that sets it; otherwise
  clients could pick their own rate-limit bucket.
- Never touch Fly.io or any cloud resource without explicit approval.

## Toolchain

- Node 26 runs the API's `.ts` directly (no build); keep `.ts` extensions in relative imports.
